# MEDULLA-WORLD-VIEW requirements

| ID | Requirement | Verification |
|---|---|---|
| `MEDULLA-WORLD-VIEW-R001` | **World-view spatial vocabulary.** The spatial vocabulary lives in the existing world-view ontology module, `crates/medulla-core/ontology/worldview-v1.ttl` (ontology IRI `https://knuckles-team.github.io/ontology/worldview`, registered as `CoreSpec { module: "worldview", version: 1 }` in `core_specs` of `crates/medulla-graph-core/src/graph/schema_sources.rs`); the world view is one domain, so it is one module and no separate spatial module or catalog entry exists. Under the shared core namespace (`https://knuckles-team.github.io/ontology/core#`) the module declares the classes `:District`, `:Building`, `:Room` and `:Street`, each `rdfs:subClassOf :Place` (the core class of `core-foundation-v1.ttl`); the object property `:hasInterior` (`:Building` → `:Room`); the datatype property `:position` (domain `:Place`) with its sub-properties `:positionX` and `:positionZ` (`xsd:decimal`); and `:extentWidth` and `:extentDepth` (domain `:Building`, `xsd:decimal`). Containment reuses the core `:locatedIn`; the module does not redeclare it. A street's route is derived placement (MEDULLA-WORLD-VIEW-R002), computed on read and never stored, so the vocabulary carries no street-vertex term. The spatial classes point at the entities the core ontology already models: agents (MEDULLA-ORCH-VOCAB-R002), agent definitions, prompt templates and workflow patterns (MEDULLA-ORCH-VOCAB-R800), connector packs (the fleet catalog, [ARBORA-FLEET-R040](https://github.com/Knuckles-Team/arbora/blob/main/specs/fleet-catalog-and-tools/requirements.md)) and agent memory (MEDULLA-DATAPLAT-VOCAB-R001). The module adds no identity, memory, orchestration or store class. Caller chain: `GraphSchemaSources::default()` → `current_core_catalog` → `core_specs` entry `module: "worldview"` (`include_str!` of `worldview-v1.ttl`); the Python package serves the same file through `medulla.ontology.module_files()`. Writes: none. Depends: MEDULLA-ORCH-VOCAB-R002, MEDULLA-ORCH-VOCAB-R800, MEDULLA-DATAPLAT-VOCAB-R001. | Test: `tests/test_world_view_ontology.py::test_spatial_classes_extend_the_core_ontology` loads the packaged world-view module and asserts the module IRI is declared, each spatial class is under the core namespace with `:Place` as its only parent, `:hasInterior` and `:position` are declared, `:locatedIn` is the core relation and is not redeclared, and no identity, memory, orchestration or store class is introduced. |
| `MEDULLA-WORLD-VIEW-R002` | **Derived layout, stored overrides.** BUILD. The deterministic placement of each connector is derived from the connector catalog and never stored; only manual overrides are stored, as `:Building` nodes with a stated reason. Module `medulla/world_view.py` (new; pure functions plus one small store class), exported from `medulla/__init__.py`. Types (frozen dataclasses): `CatalogEntry(server_id: str, group: str)` is the input shape, a sequence of which is the connector catalog (the caller builds it from the fleet catalog rows, `FleetCatalogClient.list_all`, taking each row's server id and group; a duplicate `server_id` refuses `ValueError("WORLD_VIEW_DUPLICATE_SERVER: <id>")`); `Placement(server_id: str, district: str, plot: int, x: int, z: int)`; `Override(server_id: str, x: int, z: int, reason: str)` (a blank `reason` refuses `ValueError("WORLD_VIEW_REASON_REQUIRED")`); `Layout(placements: tuple[Placement, ...], stale_overrides: tuple[str, ...])`. Constants: `PLOT_COLUMNS = 8`, `PLOT_PITCH = 20`, `DISTRICT_PITCH = 200`. `derive_placements(catalog: Sequence[CatalogEntry]) -> tuple[Placement, ...]`: the district key is the entry's `group` (an empty group is the district `ungrouped`); districts are the distinct keys in ascending byte order and the district index `d` is the position in that order; within a district the entries are sorted by `server_id` in ascending byte order and the plot index `i` is the position in that order; `x = d * DISTRICT_PITCH + (i % PLOT_COLUMNS) * PLOT_PITCH` and `z = (i // PLOT_COLUMNS) * PLOT_PITCH`; the result is ordered by `(district index, plot)`; the same catalog always gives the same tuple and the input order does not matter. `apply_overrides(derived: Sequence[Placement], overrides: Sequence[Override]) -> Layout`: an override replaces `x` and `z` of the placement with its `server_id` (district and plot stay derived); an override whose `server_id` is not in `derived` is listed in `stale_overrides` (sorted) and never applied. Override store: `class OverrideStore` with `__init__(self, client: MedullaClient)`, `async put(self, override: Override) -> None`, `async clear(self, server_id: str) -> None` and `async list(self) -> tuple[Override, ...]`. An override is the node `world:override:<server_id>` written with `generated.graph.send_add_node(client, {"node_id": ..., "properties_msgpack": <msgpack of {"type": "Building", "server_id", "position_x", "position_z", "override_reason"}>})`, removed with `send_remove_node`, and read with `send_get_nodes_by_label(client, {"label": "Building", "limit": 1000})` keeping nodes whose id starts with `world:override:`; the tenant and principal come from the connection (no request carries them). The ontology gains `:serverId` and `:overrideReason` (both `rdfs:domain :Building`, `rdfs:range xsd:string`) in `crates/medulla-core/ontology/worldview-v1.ttl`, and the `position_x` and `position_z` node properties are the stored form of `:positionX` and `:positionZ`. Derived placement is never written: `derive_placements` and `apply_overrides` perform no I/O, and `OverrideStore` is the only writer. Caller chain: the served layout read of MEDULLA-WORLD-VIEW-R003 → `FleetCatalogClient.list_all` → `derive_placements` → `OverrideStore.list` → `apply_overrides`. Depends: MEDULLA-WORLD-VIEW-R001. | Test: `tests/test_world_view_layout.py::test_derived_placement_is_never_stored` (planned) (L2, an in-memory fake client recording every `_send`): derives the layout for a catalog and adds one connector, asserts the derived tuple changed and no write was sent; `put`s one override and asserts exactly one `AddNode` with the five properties above, that the override wins in `apply_overrides`, then removes the connector from the catalog and asserts the override is in `stale_overrides` and not applied; also asserts `derive_placements` is order-independent. |
| `MEDULLA-WORLD-VIEW-R003` | **World layout envelope (client-side read over existing routes).** Class: BUILD. Decision (pass 8): the engine gains no spatial method. Spatial facts are ordinary graph facts, and the one route that reads facts is the existing client read of R002 (`OverrideStore.list` over `GetNodesByLabel`); a second served method would be a second route for the same read and a wire change. The envelope is therefore a pure function and one async reader in `medulla/world_view.py` (exported from `medulla/__init__.py`), which the arbora/overstory read path consumes. Types (frozen dataclasses): `WorldDistrict(name: str, index: int)`; `WorldBuilding(server_id: str, district: str, plot: int, x: int, z: int, overridden: bool, reason: str | None)`; `WorldEnvelope(version: int, districts: tuple[WorldDistrict, ...], buildings: tuple[WorldBuilding, ...], stale_overrides: tuple[str, ...])` with `WORLD_ENVELOPE_VERSION = 1`. `build_world_envelope(layout: Layout, overrides: Sequence[Override]) -> WorldEnvelope` is pure: districts are the distinct `Placement.district` values in ascending byte order (`_byte_order`) with `index` the position in that order; buildings keep the `layout.placements` order (district index, plot) with `x` and `z` as already overridden by `apply_overrides`; `overridden` is true and `reason` is the override's reason when an applied override named the `server_id`, else false and `None`; `stale_overrides` is `layout.stale_overrides`. `async read_world_envelope(catalog: Sequence[CatalogEntry], store: OverrideStore) -> WorldEnvelope` calls `derive_placements(catalog)`, `await store.list()`, `apply_overrides(...)` and `build_world_envelope(...)`; it performs no write. Refusals: none are added. The tenant comes from the connection (R002), so there is no tenant parameter and no unknown-tenant case; there is one layout per tenant, so there is no layout name and no unknown-layout case; a catalog with no entries gives an empty envelope (`districts=()`, `buildings=()`). Rooms and streets: the derived layout produces only buildings, so the envelope carries none (the `:Room` and `:Street` classes of R001 stay vocabulary until a producer exists); history replay compares envelopes by value (the dataclasses are frozen and comparable), with no second registry. Wire shape for callers: `dataclasses.asdict` of the envelope, tuples as JSON arrays. Writes: none. Depends: MEDULLA-WORLD-VIEW-R001, MEDULLA-WORLD-VIEW-R002. | Test: `tests/test_world_view_layout.py::test_world_envelope_is_derived_overridden_and_read_only` (planned) (L2, the in-memory fake client of R002's test): reads the envelope for a three-connector, two-group catalog and asserts the districts, building order and coordinates, then `put`s an override and asserts `overridden` and `reason` on that building and no other, adds a stale override and asserts it is listed and not applied, asserts an empty catalog gives the empty envelope, and asserts no write was sent by `read_world_envelope`. |
| `MEDULLA-WORLD-VIEW-R004` | **Revisioned city-state facts.** BUILD. City state is ordinary graph facts, as R003 decides. `worldview-v1.ttl` declares `:CityPresence` (parent `:Place`) with `:presenceKind` (`npc`, `ai` or `human`), `:worldX`, `:worldY`, `:heading`, `:activityState`, `:targetRef`, `:observedAt`, `:expiresAt` (human only), `:presenceSubject` and `:revision` (integer). `medulla/world_view.py` gains `CityStateReader.snapshot(tenant) -> CityStateSnapshot { revision, simulated_at, layout_revision, entities }` over `GetNodesByLabel`, where `revision` is the highest entity `:revision`. It gains `CityStateWriter.heartbeat(subject, expected_revision, x, y, heading, activity_state, target_ref)`, which writes the subject's one `human` node through `CompareAndSetNodeFields` on `:revision`. `activity_state` is one of `walking`, `driving`, `flying`, `sailing` and `inside`, and the writer stores it as `:activityState`. `target_ref` is an opaque city id matching `^[A-Za-z0-9._:-]{1,128}$`, or `None`, and the writer stores it as `:targetRef` or removes the property. Any other `activity_state` or `target_ref` refuses `INVALID_ARGUMENT` before the write. The snapshot returns both fields for every entity. A stale `expected_revision` refuses `REVISION_CONFLICT`. A write for another subject refuses `SUBJECT_ACCESS_DENIED`. `ai` and `npc` nodes change only from recorded run transitions. No new method exists. Caller chain: arbora `fleet.city.presence` -> `CityStateReader.snapshot`; arbora `fleet.city.presence.heartbeat` -> `CityStateWriter.heartbeat` -> `Method::CompareAndSetNodeFields`. Shape: vocabulary lines in `worldview-v1.ttl`; two small classes in `medulla/world_view.py`. Depends: MEDULLA-WORLD-VIEW-R003. The owning change adds each new file named here. | Test: `tests/test_world_view_city_state.py::test_snapshot_is_revisioned_and_heartbeat_is_subject_bound_and_fenced` and `::test_heartbeat_stores_activity_and_target_and_refuses_unknown_values` (L2). |
