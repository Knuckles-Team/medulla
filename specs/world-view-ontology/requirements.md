# MEDULLA-WORLD-VIEW requirements

| ID | Requirement | Verification |
|---|---|---|
| `MEDULLA-WORLD-VIEW-R001` | **World-view spatial vocabulary.** The spatial vocabulary lives in the existing world-view ontology module, `crates/medulla-core/ontology/worldview-v1.ttl` (ontology IRI `https://knuckles-team.github.io/ontology/worldview`, registered as `CoreSpec { module: "worldview", version: 1 }` in `core_specs` of `crates/medulla-graph-core/src/graph/schema_sources.rs`); the world view is one domain, so it is one module and no separate spatial module or catalog entry exists. Under the shared core namespace (`https://knuckles-team.github.io/ontology/core#`) the module declares the classes `:District`, `:Building`, `:Room` and `:Street`, each `rdfs:subClassOf :Place` (the core class of `core-foundation-v1.ttl`); the object property `:hasInterior` (`:Building` → `:Room`); the datatype property `:position` (domain `:Place`) with its sub-properties `:positionX` and `:positionZ` (`xsd:decimal`); and `:extentWidth` and `:extentDepth` (domain `:Building`, `xsd:decimal`). Containment reuses the core `:locatedIn`; the module does not redeclare it. A street's route is derived placement (MEDULLA-WORLD-VIEW-R002), computed on read and never stored, so the vocabulary carries no street-vertex term. The spatial classes point at the entities the core ontology already models: agents (MEDULLA-ORCH-VOCAB-R002), agent definitions, prompt templates and workflow patterns (MEDULLA-ORCH-VOCAB-R800), connector packs (the fleet catalog, [ARBORA-FLEET-R040](https://github.com/Knuckles-Team/arbora/blob/main/specs/fleet-catalog-and-tools/requirements.md)) and agent memory (MEDULLA-DATAPLAT-VOCAB-R001). The module adds no identity, memory, orchestration or store class. Caller chain: `GraphSchemaSources::default()` → `current_core_catalog` → `core_specs` entry `module: "worldview"` (`include_str!` of `worldview-v1.ttl`); the Python package serves the same file through `medulla.ontology.module_files()`. Writes: none. Depends: MEDULLA-ORCH-VOCAB-R002, MEDULLA-ORCH-VOCAB-R800, MEDULLA-DATAPLAT-VOCAB-R001. | Test: `tests/test_world_view_ontology.py::test_spatial_classes_extend_the_core_ontology` loads the packaged world-view module and asserts the module IRI is declared, each spatial class is under the core namespace with `:Place` as its only parent, `:hasInterior` and `:position` are declared, `:locatedIn` is the core relation and is not redeclared, and no identity, memory, orchestration or store class is introduced. |
| `MEDULLA-WORLD-VIEW-R002` | **Derived layout, stored overrides.** The spatial layout of a served city is stored as spatial facts of a tenant. The deterministic placement of each connector — its district, plot and position — is derived from the connector catalog (server id and group); the derived placement is never stored. Only explicit manual overrides are stored, as facts with a stated reason, and an override supersedes the derived placement for the connector it names. A connector added to the catalog appears in the derived layout without a write, so the layout cannot drift from the fleet. Removal from the catalog removes the derived placement; a stored override for a removed connector is reported as stale, never applied. Caller chain: (planned) the world-view layout derivation over the tenant's connector catalog facts. Shape: (planned) the layout derivation and override store in the world-view module, reusing the core ontology's existing entity classes for the pointed-at endpoints. Depends: MEDULLA-WORLD-VIEW-R001. | Test: `tests/test_world_view_layout.py::test_derived_placement_is_never_stored` (planned) derives the layout for a catalog, adds one connector, and asserts the derived placement changed while the stored facts contain only overrides. It overrides one connector, asserts the override wins, removes the connector and asserts the override is reported stale. |
| `MEDULLA-WORLD-VIEW-R003` | **Spatial facts query method.** Spatial facts are served through one method: the world layout of a tenant — its districts, buildings, rooms and streets with `locatedIn`, `position` and `hasInterior`, and its active overrides. The method answers from stored facts only (derived placement is computed on the read); a read never writes. Unknown tenant or unknown layout refuses with a typed reason. The answer is a stable envelope so a consumer can render it and replay recorded history against it without a second registry. Caller chain: (planned) the served spatial query method of the engine. Shape: (planned) one method over the world-view module's read path, reusing the engine's existing typed-query envelope. Depends: MEDULLA-WORLD-VIEW-R001, MEDULLA-WORLD-VIEW-R002. | Test: `tests/test_world_view_served.py::test_spatial_query_serves_the_layout_and_refuses_unknown_tenants` (planned) serves a seeded tenant layout and asserts the full envelope (districts, buildings, rooms, streets, relations, active overrides); it asserts an unknown tenant and an unknown layout each refuse with a typed reason and no write. |
