# Research: engine parity

Decisions that shape the rows. Current state only.

## Sequences persist in the existing allocator table

A named sequence needs durable state, and a new owner table is a storage layout
change with a frozen predecessor census and an offline upgrade. The per-table
`__sql_seq__` allocator already holds `name -> u64`. A sequence is four `u64`
entries under a NUL-prefixed key that no table name can equal, written in one
maintenance transaction. `R013.2` moves the serial counters onto the same keys.
A later layout change may give sequences their own table.

## One SQLSTATE table, shared by the wire and the store errors

`crates/medulla-wire-core/src/wire/sqlstate.rs` is the only table from engine
code to SQLSTATE. `user_err` of the wire core and of the pgwire front end both
read it, so a store error that starts with `<CODE>: ` reaches the client with its
state and an unlisted code keeps `58000`.

## COPY out is a plain read

`COPY <table> TO STDOUT` runs `SELECT <columns> FROM <table>` through the
authorized read path, so access control and masking are those of a `SELECT` and
no second policy path exists. Binary COPY out is refused with
`FEATURE_NOT_SUPPORTED`.

## Partial and expression indexes are never a plain lookup

A partial index omits rows and an expression index keys a derived value, so a
first-column lookup or an ordered read on the raw column ignores them. Only a
planner that proves the query implies the predicate (`R010.2`) uses a partial
index.

## Decision: where the footprint is validated and how the history is configured (R002.2)

The keys a transaction reads and writes are the rows its `UPDATE` and `DELETE` matched and the rows its inserts and updates wrote, and the store only knows them once the ops run inside the write transaction. Validation therefore runs there, after the ops are staged and before the commit point, and a conflict aborts the transaction; redb discards every staged row, so nothing is written. This is exact and needs no second scan of the table. The write set is recorded in the ring inside the same serialized write transaction, so no commit validates between the record and the commit point; a failure before the commit point retracts the record. A pinned footprint older than the ring refuses with `TXN_SNAPSHOT_EXPIRED`. The history size follows the precedent of the enqueue timeout of R001.1: an environment variable (`MEDULLA_TABLES_OCC_HISTORY_COMMITS`) that parses and clamps into the documented bounds. The `ON CONFLICT` insert path is not a buffered `TxnOp`, so it runs auto-commit and never carries a footprint.

## Decision: row changes reach the feed through the tenant store (R015.1)

The change feed is the one `CdcHub`; the table store owns no feed. The hub is the store's `RowChangeSink`, installed by `handle_sql` on the tenant store before any statement runs (the store keeps the first sink it is given, so a repeat install is a no-op). A feed event of a row is one `Row { table, operation, key }` change on `ReadGraphChanges`, never a second method. Reading rows needs the `cdc:read` scope and read access to the table (`sql_catalog_acl::may_stream_table`: owner, admin or SELECT grantee, and no row-level column, because the stream carries every row and a row-level table is filtered per caller). The ring size is the registry knob `cdc.ring_events`, replacing the `MEDULLA_CDC_RING` environment variable, so one registry owns the tunable and a served test can move a cursor out of the window with a bounded number of commits.
## Wire login verifier forms (R007.1)
Decision: the `Password` verifier is the SCRAM salted credential, not the bare stored key. pgwire's SCRAM server API takes the salted password (it derives both the client-proof check and the server signature from it), so a stored key alone cannot complete the exchange. The plaintext password is never stored. A `Certificate` verifier is the SHA-256 of the client certificate (DER) because the TLS session exposes the certificate chain, not a parsed public key. A `Token` verifier is the SHA-256 of the token. The record lifecycle is the explicit machine `wire_login` (`Active --Revoke--> Revoked`); `revoked_ms` is the datum written by the transition.

## Wire login tenant check (R007.2)

A login record names a tenant. The connection's verified authority carries one tenant (the deployment's request policy). After the actor is bound, the two must be equal; a mismatch refuses the first query with `PLAN_SCOPE_UNVERIFIED` (SQLSTATE `28000`, one row in the sqlstate table) and no read runs. Wire reads add no second filter: the principal is the actor of the existing authorized read path, and the served test compares it with `Method::Uql` for three principals.

## R012.1 triggers

A trigger is a statechart embedded in its table's schema record (`TriggerSpec.machine`, with `machine_id` its content id), so a write is a pure call to `transition` and needs no second store read; the statechart store is not consulted. The row reaches the machine as flat `new.<column>` and `old.<column>` keys so the existing guards and `Assign` actions work on columns without a nested-map action. The refuse action is an `Emit` whose signal is `refuse` or `refuse:<message>`. A multi-row insert runs its triggers row by row inside the one write transaction; a refusal rolls the whole statement back. A before-insert machine sees only the supplied columns (defaults and serial values are filled after it). No layout change: the `triggers` field is skipped when empty, so a table without triggers keeps its stored bytes (no LAYOUT-REGEN).

## R011.1 deferred foreign keys

A deferred key is checked by one pass after the last op of the transaction, over the keys the transaction recorded, never over whole tables: an insert or update records the child keys its rows carry (skipping a key that did not change), and a delete or update records the parent keys its rows held. The pass checks each recorded key once. A child key resolves when the parent holds it; when it does not, the child still has to carry it for the key to refuse, so a row a later op removed or moved never refuses. A parent key is clear when the parent still holds it or no child carries it. Lookups use a secondary index on the key's first column when one exists, and one scan otherwise (the same cost as an immediate key's per-row check). The pending set is a registry knob (`tables.deferred_fk_pending_max`) because the store cannot see the registry: the composition root installs the resolved value on the store, as it installs the change-feed sink, and a store without an installed value (an ephemeral store, a test store) uses the knob's registry default, never zero: the default is one constant in `medulla-tables` that the registry takes as its default, so there is one source and no `DEFERRED_FK_LIMIT_UNSET` refusal. The row's count probe is an engine metric (`deferred_fk_keys_checked`), not a test seam. Cascading and SET NULL actions stay immediate; only NO ACTION is deferred, as in PostgreSQL. The four violation codes are carried as message prefixes (`UNIQUE_VIOLATION`, `FOREIGN_KEY_VIOLATION`, `CHECK_VIOLATION`, `NOT_NULL_VIOLATION`), which the R006.1 table maps to SQLSTATE; a NOT NULL refusal names its column and a foreign-key refusal names its constraint. No layout change (the new fields are skipped when false).
A deferred key is checked by one pass after the last op of the transaction: the pass re-validates, through the existing `validate_existing_fk_children_in`, every row of each table the transaction wrote (or whose deferred key references a written table). That finds an unresolved reference whichever op left it (a child inserted before its parent, a parent deleted without its children). Cascading and SET NULL actions stay immediate; only NO ACTION is deferred, as in PostgreSQL. ## R010.2 index statements and the partial-index planner

`CREATE [UNIQUE] INDEX` is decoded from the parsed statement (`classify/index_plan.rs`); the pgvector ANN spelling is still recognized textually first, so a scalar index never reaches the ANN registration. `DROP INDEX name` has one statement kind, `DropIndex` (hard cutover from `DropAnnIndex`): the name resolves through the ANN catalog first, then the ordinary catalog, and the authorizing table is the same one the ANN drop already checks, so a name the caller may not alter reads as absent. Index names are unique across the owner's tables for ordinary indexes.

The planner step lives in `UserTableProvider::scan`. Each query conjunct that is `column OP literal`, `column [NOT] IN (...)` or `column IS [NOT] NULL` becomes a `CheckExpr` leaf; a partial index serves the scan when every conjunct of its predicate equals a leaf (literals compared as the cells the column stores). Those filters are reported `Inexact` only when the table has a partial index, so DataFusion still re-applies the full filter and the index can only narrow. The scan is wrapped in `IndexScanExec`, which forwards execution and prints `IndexScanExec: index=<name>` so `EXPLAIN` names the index.

## R009.2 refusing a form outside the matrix

The refusal sits where classification finds no served kind, not at the top of `classify`: a statement that a classifier arm serves never pays a second lookup, and the form name is derived from the parsed statement's leading keywords (`CREATE TRIGGER ...` is `create_trigger`). `refuse_form` consults one cached `PgCompatibilityMatrix::with_served_forms()`; a `Refused` or absent form reads "`<form>` is not supported", and a served form whose particular shape no arm decodes keeps its detail. Both carry the `FEATURE_NOT_SUPPORTED` code, which the one SQLSTATE table maps to `0A000`. The matrix now lists `copy_out` (the R006.1 form the R009.1 list had missed) and `create_index`; `every_supported_entry_has_a_test` holds one sample per `Supported` or `Partial` entry (statements classify to their own form; functions are reads, and those with pinned argument shapes run) and fails when a matrix entry has no sample or a sample names a form the matrix does not serve.
`InstanceStatus`, `StatechartInstanceStatus` and `SqlFormState` are real closed state sets, so each gets an explicit machine. `InstanceStatus` follows the instance configuration (a parallel chart can enter and leave a final state while another region fires), so no state is terminal and the events are `Remain`, `ReachFinal`, `LeaveFinal` and `RemainFinal`; the store settles the status with `InstanceStatus::settle`, which picks the event from the current state and the configuration and applies it. `SqlFormState` starts `Refused` (the matrix is closed) and moves by `ServePartially`, `ServeFully`, `Narrow` and `Withdraw`; entries are built with `SqlFormEntry::served_as`.

## R013.2: serial columns allocate through named sequences

Decision: a serial value comes from the column's sequence `<table>_<column>_seq`, allocated inside the insert statement's own write transaction (the high mark advances with the statement and rolls back with it), not from the in-memory block that `nextval` serves. The block cache exists to avoid a durable write per `nextval` call; an insert already holds the write transaction, so the allocation is free and a refused statement leaves at most a gap. Values drawn by `nextval` from a cached block are always below the persisted high mark, so the two paths never issue the same value. The per-table `rowid` counter stays as the physical row key only and is no longer read to derive a serial value. Existing tables created before this change are upgraded offline, consistent with CQ-ORCH-R810.4: named sequences live in their own owner table `__sql_sequences__`, so the SQL layout digest changes and a normal open of the old file refuses with `SQL_FORMAT_UPGRADE_REQUIRED`. The registered upgrade (`SQL_BEFORE_NAMED_SEQUENCES`, run by `store-upgrade`, also reached from the two older SQL predecessors) moves the named sequences out of `__sql_seq__`, then creates `<table>_<column>_seq` for each serial column of the catalog with `high_mark = counter + 1` (the old engine issued `rowid + 1` and the counter is the next rowid). The catalog and counters are not tenant-keyed but sequence keys are, so the upgrade seeds each tenant scope whose SQL bootstrap scope the file has bound (read from the scope bindings) and refuses, typed and with the file untouched, when serial columns exist and no scope has served them. The rowid counter is not deleted: it is still the physical row key. LAYOUT-REGEN needed: the pinned SQL layout digest in `lineage.rs` (`pinned_layout_digest`) is refreshed by the gate fixer; the predecessor digest (`PRE_NAMED_SEQUENCES`) is the previous pin. The point-get pushdown on serial equality in `crates/medulla-sql/src/provider.rs` stays correct because it already re-verifies the fetched row and falls back to the scan.

### R012.2 trigger nesting, depth and reaction ledger (design calls)
A table-writing trigger is an `After` machine whose `Custom` effects (`insert_row`, `update_rows`, `delete_rows`) name a table, a row or assignments and an equality selector; `{"from": "<context key>"}` reads the machine context. The write runs through the same write path, so the target table's triggers react one level deeper. A `Before` machine may only rewrite or refuse (its table handle is open during the write), so a `Custom` effect on a `Before` machine refuses `TRIGGER_MACHINE_INVALID`. The depth bound is the registry knob `tables.trigger_depth_max` (default 16, one constant in `medulla-tables`); the store cannot see the registry, so the composition root installs the resolved value (`install_trigger_depth_max`) and an uninstalled process uses the default. The reaction ledger is the owner table `__sql_trigger_reactions__` (append-only `TriggerReaction{event_id, trigger, statement_id}` under one key per scope, write chain, event and trigger). `event_id` is the content digest of the row event (table, timing, kind, old and new row); `statement_id` is one id per top-level row event, allocated from a per-scope counter in the same table, so it never repeats across restarts. A reaction whose key already exists refuses `TRIGGER_REACTION_DUPLICATE` (a cycle that re-creates the same event). The layout change goes through the offline upgrade registry (`SQL_BEFORE_TRIGGER_REACTIONS`, CQ-ORCH-R810.4). LAYOUT-REGEN needed: `PRE_TRIGGER_REACTIONS` in `crates/medulla-storage/src/owner/sql_checkpoint_upgrade/contract.rs` is a placeholder until the digest-printing test runs.

### R012.2 trigger DDL (design calls)
`CREATE TRIGGER name {BEFORE|AFTER} events ON table EXECUTE MACHINE machine_id` and `DROP TRIGGER name ON table` are parsed textually (`trigger_ddl.rs`, as `sequence_ddl.rs`); the PostgreSQL `EXECUTE FUNCTION` shape is not this engine's trigger and stays a refused shape of the served `create_trigger` form. The table store cannot see the statechart store, so `medulla-server` installs one `TriggerMachineSource` (the engine's statechart store, one open handle per persistence directory) and `resolve_trigger_spec` builds the `TriggerSpec` before the transaction op is staged; an unknown id refuses `TRIGGER_MACHINE_INVALID` and writes nothing. `TxnOp::CreateTrigger`/`DropTrigger` are admin-only like every other catalog-wide DDL op and run in the same write transaction as other DDL. The compatibility matrix lists `create_trigger` and `drop_trigger` as `Supported`; the unlisted-form tests use `create_policy`.

### R008.1 catalog constraints and indexes (design calls)
One list of constraints feeds `pg_constraint`, `information_schema.table_constraints` and `information_schema.key_column_usage`, derived from the stored table schemas (column flags plus `TableConstraint`s), so the three views cannot disagree. A column-level `PRIMARY KEY`, `UNIQUE` or `CHECK` becomes a constraint named as `TableSchema::constraint_display_name` names it (`<table>_pkey`, `<table>_<column>_key`, `<table>_<column>_check`); a flag a table-level constraint already states is listed once. `pg_index` lists the ordinary secondary indexes only (`SecondaryIndexSpec`); `indkey` holds 1-based column numbers and 0 for an expression column. The store catalog read (`StoreCatalog`) now also reads the table schemas and the index list once per statement, inside the existing context cache epoch, which already covers `CREATE TABLE` and `CREATE INDEX`. The ten shaped-empty `pg_catalog` relations are listed in one function; any other absent catalog relation keeps `42P01`.

### R006.2 refusing a protocol message the engine does not implement (design calls)
The stock `process_socket` ends a connection on any frame decode error, and the decoder reports the `FunctionCall` tag (and any other unknown tag) as `InvalidMessageType`. The engine therefore owns its connection loop (`message_loop.rs`), identical to the stock one except for that branch: for a tag in a closed table (`FunctionCall`, `CopyBoth`) it drops the frame by its declared length, rebuilds the framed stream (a decode error leaves the framed stream terminal), and refuses with `FEATURE_NOT_SUPPORTED`. An unknown tag outside the table still ends the connection. The refusal depends on the connection state: ready or in a query, the typed error and `ReadyForQuery`; discarding to `Sync`, silent (the protocol says so); startup, authentication or `COPY`, the fatal protocol error, because the stock error path moves a connection to ready and an unauthenticated connection must never get there through a refusal. The loop's startup timeout is the registry knob `pgwire.startup_timeout_ms` instead of the stock constant. The served test uses a TCP relay that injects the raw frame at a frame boundary and withholds the answer from the client library, since no client library sends these messages.

### R019.2 outside databases are sources only (design calls)
The check of a write-back change set's `target_class` runs before the actor and key checks: it depends only on the class, so a refusal carries no information about the caller's other claims and writes nothing. A class names a durable engine store by file name (`rbac.redb`), by stem (`rbac`) or as the Agent Library physical store, through the one list `durable_stores::DURABLE_STORES`; there is no second list. `target_class` is optional and skipped in the encoding and digest when unset, so a change set without it keeps its digest. The endpoint-scheme refusal is one function (`check_endpoint_scheme`) used by `validate` (secret reference carrying a url) and by a caller that has resolved the endpoint; `admit_backend_setting` maps it to `EXTERNAL_PLACEMENT_FORBIDDEN`. The served test does not attach a source: the engine never calls a source, so "no write to the source" is shown by the refused change set leaving no row and the engine refusing to open a backend placed in an outside database.
The served test drives pgwire only: 16 sessions insert disjoint valid rows into one table with a primary key, a foreign key and a check, wait on a barrier, then each probes a key another session owns, a missing parent and a negative balance. The bench group `constraints` compares single-row insert commits into a constrained and an unconstrained table in one store, so the 15 percent budget measures the checks alone; its baseline entry sits in `benches/baselines/engine_parity.json`.
